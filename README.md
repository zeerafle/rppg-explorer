# rPPG Explorer

An interactive, browser-based walk-through of remote photoplethysmography (rPPG): how a camera reads a
pulse, and how video compression breaks it. Built to *understand* the thesis topic, not to publish.
Vue 3 + Vite, D3 scales/shapes for the charts, KaTeX for the equations.

```bash
npm install
npm run dev            # http://localhost:5173
npm test               # JS signal code vs the Python experiment code
```

## Modules

| # | Module | What you do |
|---|---|---|
| 0 | The big picture | Five-step pipeline, key numbers, glossary |
| A | Waves and frequency | Sine wave knobs (Hz/bpm, amplitude, phase), adding waves, the real pulse as a wave |
| B | Sampling a signal | Aliasing and Nyquist; drop frames from the real pulse and watch the estimate |
| C | Fourier and the spectrum | Spectrum of a noisy sum, window length vs resolution, leakage and the Hann taper |
| D | Filters and harmonics | Band-pass on the real trace; shapes and their harmonic combs (links to the keyframe comb) |
| 1 | Pulse in the colour | Watch a colour-magnified video; heat map of which face tiles carry the pulse |
| 2 | Video to colour trace | Play the video with the region box and the live R/G/B trace; average more tiles |
| 3 | Colour to pulse | Step through POS / CHROM on a 1.6 s window; add flicker and see green-only fail |
| 4 | Pulse to heart rate | Window, Hann taper, FFT, peak; coarse vs fine frequency grid |
| 5 | What compression does | Real keyframe positions, QP per frame, decoded-minus-original clip, 42-subject damage curve |
| 6 | The keyframe artefact | Eight-step walk-through of why the estimate locks on ~60 bpm, and the partial fix |
| 7 | What we found | Results table, QP-gate risk-coverage demo, open questions |
| 8 | Lab | Subject x encode x algorithm x window, all at once |

## How-to-read panels

Each module has a "How to read this" side panel (right column on wide screens, collapsible block on narrow ones). Its text lives in `src/lib/howto.json`, keyed by module id, rendered by `src/components/HowToRead.vue`.

## Data is real, not simulated

`public/data/` is git-ignored (it holds clips of real faces from UBFC-rPPG); rebuild it with the commands below. Everything under `public/data/` is produced by `data-build/build_data.py` from the UBFC-rPPG recordings in
`~/Projects/qp-probe/ubfc-rppg` and the experiment outputs in the thesis repo, using the same Python
(`qp-probe/pilot/extract.py`, `keyframe.py`) as the experiments. The only things added by hand are labelled
`illustration` in the UI (the sawtooth toy, the flicker experiment).

```bash
python data-build/build_data.py                      # all stages, each cached
python data-build/build_data.py --stage subjects     # one stage; see the docstring for the list
python data-build/encode_variance.py                 # re-encode subject 10 several times (see below)
```

Needs ffmpeg with libx264 and libvpx-vp9, and Python with numpy, scipy, pandas, opencv-python-headless.
`public/data` is about 500 MB (videos in both H.264 and VP9; the browser takes the first it can play).

## The JavaScript is tested against the Python

`src/lib/dsp.js` ports POS, CHROM, the Butterworth `filtfilt`, the zero-padded Hann periodogram and the
heart-rate peak picker. `tests/dsp.test.js` compares them with outputs of the Python code on subject 10 (POS
trace to 1e-6, per-window heart rates, spectrum shape). `tests/golden.json` is regenerated by the `golden`
stage. The pooled keyframe numbers (82 / 61 / 40 % of windows on a keyframe harmonic vs 9 / 18 / 28 % by
chance) were also reproduced independently in JS.

`npm run dev` plus `node tests/shots.mjs` (screenshots of every module) and `node tests/interact.mjs`
(steps through the keyframe walk-through, checks video playback drives the chart) need `playwright-core`
and a Chromium; the scripts point at `~/.cache/ms-playwright`.

## Things to know

- **x264 is not bit-reproducible.** Encoding the same file twice with default (multi-threaded) settings
  gives different streams, and for some conditions different heart-rate errors. `-threads 1` is
  deterministic. Subject 10 here is a *fresh* encode (the original run's file was not kept), so a few medians
  differ from `Proposal/experiments/keyframe-2026-10-07/FINDINGS.md`; `public/data/hero/encode-check.json`
  and `encode-variance.json` quantify it. The 1 s and 2 s keyframe effect is robust to re-encoding; 4 s,
  intra-refresh and the single-keyframe baseline are not, for a single subject.
- Subject 10's trace, QP and frame types are measured on the *shipped* streams, so the video and the charts
  next to it agree frame for frame.
- The decoded-minus-original clip shows spatial error only; the keyframe pump (about 0.2 grey levels of
  face-average brightness) is invisible in any per-pixel view and shows up only after averaging.
- Colour magnification uses a band around this subject's heart rate (84 to 132 bpm); motion in that band is
  amplified too, so hair edges ghost.
